How a booking becomes an invite

Booking never waits for Microsoft. Every step is recorded and retried.

Step 1 1

Someone books

  • • Student picks a slot or joins a group
  • • Tutor schedules or moves
  • • CTL moves or cancels
touch_app Saved at once
Step 2 · Platform 2

The platform records it

  • • One row in tutoring_sessions
  • • One event: Created, Rescheduled, Cancelled, Attendee added
  • • Old fields kept in step by one mirror module
database One transaction
Step 3 · Queue 3

The queue

  • • Each event waits in outbox_deliveries
  • • Same database transaction as the booking
  • • Booking never waits for Microsoft
hourglass_top Nothing waits
Step 4 · Worker 4

The worker

  • • Takes events in order per session
  • • Retries after 1, 5, 15, 60 minutes
  • • Gives up after 8 tries and tells CTL
published_with_changes Retries with backoff
Step 5 · Microsoft 5

Microsoft 365

  • • Outlook invite in the organizer's calendar
  • • Teams link generated for online sessions
  • • Attendees: student, tutor, CTL, counselor
cloud_done Microsoft Graph, server side
reply status flows back

Two organizer modes

Configurable via CTL Integration Panel based on departmental governance:

Tutor's own calendar Delegated

The tutor organizes the meeting and controls the Teams lobby directly from Outlook.

Shared CTL mailbox Centralized

All appointments are centralized under ctl-tutoring@ku.ac.ae without direct tutor delegation.

Toggleable in CTL Settings without code deployments

Login does not change

Zero credential exposure or disruption to current user authentication:

  • key Standard auth: Username and password unchanged
